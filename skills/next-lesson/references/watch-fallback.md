# Watch fallback for a CLI without `altitude watch`

Load only after `altitude watch start` returns no JSON result with an `outcome`, as specified in SKILL.md. Use these shell mechanics for the rest of the session, without retrying the command path at each gap. The text below is the 0.6.1 watch span, preserved verbatim, including its POSIX and PowerShell commands and replay misses. The shared teaching rules in SKILL.md still apply: chat outranks the watch on either host, and a learner who has already spoken during a fill-in has absorbed its expiry question. Hold the one-time `altitude update` nudge for session close; never block the lesson on updating.

**The watch.** Poll the file's modification time from a shell call for **3 minutes in all** per watch, using a command that exists on their system — macOS/Linux: `stat -f %m "$f" 2>/dev/null || stat -c %Y "$f"` in a sleep loop; PowerShell: `(Get-Item "$f").LastWriteTime.Ticks` with `Start-Sleep` (`stat` does not exist there at all). **The watch starts in the same turn that hands the gap over.** How it runs depends on one capability of your host, and on either kind of host you never end a turn on a promise to watch with no poll running: "I read it the moment the markers are gone" is a promise only a running poll keeps, and a turn that ends on it with nothing polling leaves the learner's save unseen and the expiry question and the stop below unreachable. **The baseline is taken once, when the watch is armed, and carried as a literal value into every command that watches after it.** Read the modification time right after you write the skeleton, and pass that number into the watching command as a literal (`base=1758384094`; PowerShell: `$base = 638939808940000000`, the `Ticks` value): every chunk and every re-armed watcher compares against the number you carry, never against a fresh reading taken when the command starts. A command that opens with its own `stat` makes whatever happened between commands its starting point — a save that landed while you were reading a result, writing a message, or issuing the next call becomes the new baseline and is never seen. For the same reason every watching command compares once before its first sleep, so a save that landed while nothing was polling is caught the moment the next command starts. Re-take the baseline only when you read the file in response to a change, and take the time first and read the file second, so a save that lands while you are reading is already later than the number you carry on. **The call that reads the baseline also checks that the marker is still in the file.** Count the markers in that same call (`grep -c 'TODO(you)' "$f"`; PowerShell: `(Select-String -SimpleMatch 'TODO(you)' $f).Count`): "right after you write the skeleton" is still seconds on a slow host, and a learner can finish a one-line gap inside them. A file that already holds fewer markers than you wrote has changed under you, and the time you just read is the time of their save, not of your skeleton: never arm a watch on it — read the file and respond as you would to any save. The miss, in replay: a tutor read its baseline 24 seconds after writing the skeleton; the learner had saved 9 seconds earlier, the finished code's time became the baseline, and chunk after chunk printed `WAITING` at code that was already finished. **Code in the gap is the learner's code, however fast it arrived.** The seconds between your calls are often half a minute on the learner's side, and you cannot feel them pass. Never doubt a save for its speed, and never write the marker back over code the learner saved — not to "reopen" the gap, not to get cleaner evidence, not for any reason: review what is there. The miss, in replay: a tutor whose baseline call ran 35 seconds after its skeleton found the body written, told the learner it had appeared "before you had a chance to type", and replaced their finished work with the marker. **The window's deadline is taken once too, when the window opens, and carried as a literal beside the baseline.** Read the clock when you arm the watch (`date +%s`), add the 3 minutes, and pass the sum into the watching command as a literal clock time (`deadline=1758384274`; PowerShell: `$deadline = 638939810740000000`, from `(Get-Date).AddMinutes(3).Ticks`). `EXPIRED` means one thing on every host: the clock has passed the deadline you carry. A command never measures the window from its own start — a `$((SECONDS+25))` counted from a command's first line is that command's own running time, not the window — because a command's start is not the window's start: it may be the second chunk of a window, or a watcher restarted halfway through one. A new window, with a new deadline, opens only when the one you carry has passed (the next gap you hand over arms its own watch, with its own two numbers); every other command that watches — the next chunk, the silent re-arm, a watcher restarted after a turn of yours — gets the remainder, never a fresh 3 minutes, and a work-in-progress save moves the baseline and never the deadline. That is what keeps the expiry question at 3 minutes instead of at the end of whichever command happened to be running, and why four windows stay about 12 minutes however many commands it took to watch them.

**If your host can run a command in the background and wake you when it exits, the watch is a background command and your message ends the turn.** Claude Code is the example: the Bash tool's `run_in_background`, whose exit re-invokes you with the command's output. A shell `&` is not this — nothing wakes you when it exits. If you are not certain your host wakes you, it does not, and the next paragraph is yours. One command is one 3-minute window: it takes the baseline you carry as a literal and the deadline beside it, compares once before its first sleep, loops on a short sleep, and exits on the first of three outcomes, printing which — the time moved and no marker is left in the file (`grep -q 'TODO(you)' "$f"`; PowerShell: `Select-String -Quiet -SimpleMatch 'TODO(you)' $f`) → `SAVED`; the carried deadline passed → `EXPIRED`; the time could not be read → `POLL_ERROR`. A save that still carries a marker never wakes you at all: the command does that silent re-arm itself, and keeps waiting from the new time, toward the same deadline. A re-armed watcher gets the same carried baseline, never the time at re-arm — after the expiry question, after a chat turn, after any turn of yours: a save that landed while you were mid-turn, with no watcher live, is a change against the number you carry, and the new watcher reports it at once. The deadline travels the same way: a watcher re-armed inside a window gets that window's deadline, so it runs for what is left of the 3 minutes, and only the watcher you start after `EXPIRED` gets a new one. Start the command, then end the turn with what the learner needs to read — the introduction and handover, the expiry question, the review — as your reply, the final message of the turn: on such a host a message written before a long tool call is the one the learner may never get, and the final message is the one they always do. Never run this watch in the foreground there, and never sleep, poll, or wait in the turn after starting it; the exit wakes you, and that wake is the next window's start or the review. The host shows the learner the command's description, so write it for them ("Watching type-sandbox/index.ts for your save") and put no hint in it. Where the tool takes a timeout, set it above the window. **One live watcher per gap**: before you start a watcher, stop the one still running (Claude Code: TaskStop), and never start a second because a chat turn came in — the running one survives your turns and still wakes you. When the gap is finished, reviewed, or abandoned, stop its watcher.

**Otherwise the watch runs in the foreground** (Codex today). Keep each shell call under your tool's timeout — set the call's timeout explicitly when your tool takes one, otherwise chain shorter sleep loops back to back; several calls make one window and one baseline, and the total is still 3 minutes. Each chunk after the first is handed the armed baseline as a literal and takes no reading of its own: seconds pass between one chunk returning and the next one starting, and those seconds are part of the window too. **A chunk ending is not the window ending.** Each chunk is handed both literals, the baseline and the deadline, and ends on the first of four outcomes, printing which: `SAVED` and `POLL_ERROR` as above; it prints `EXPIRED` only when the carried deadline has passed; and when it has merely reached the end of its own slice of your tool's timeout it prints `WAITING`. `WAITING` is not news: issue the next chunk at once with the same two literals — no message to the learner, no question, nothing in chat at all — and keep chaining until a chunk says something else. The miss, in replay: a tutor's 25-second chunks each set `deadline=$((SECONDS+25))` and printed `EXPIRED` when that ran out; the tutor read its own slice running out as the window's expiry and asked "Still working, or want a hint?" 31 seconds into a 3-minute watch, to a learner who was mid-line. The other miss, in replay: a tutor chained 25-second chunks that each opened with `last=$(stat …)`; the learner's finished save landed in the 11 seconds between two chunks, became the next chunk's baseline, and five more chunks reported no change while the finished code sat unreviewed. The message that writes the skeleton and tells them to replace the markers and save does not stop there — issue the first poll chunk before that turn ends.

Read the poll's own outcome before reading anything into its result: a polling command that errors every iteration is indistinguishable from a learner who typed nothing, and recording that as a struggle is a false evidence entry.

**A save with a `TODO(you)` still in the file — or with a marker deleted and nothing written in its place — is work in progress, not a submission.** When the modification time moves, read the file; if any `TODO(you)` marker remains, or a gap stands empty where one of them used to be, re-arm the watch silently — no review, no comment, not even "I see you've started." — from the time you took just before that read, never from a time taken after it. On a background host the watcher has already ignored every save with a marker in it, so what still wakes you is the emptied gap, and the silent re-arm is a turn with one tool call — the new watcher — and no reply text at all (where your host will not end a turn on nothing, the whole reply is "Still watching."). Editors that autosave fire on every pause, and half a line reviewed as if it were finished is a correction nobody asked for. The empty gap is that same half-finished state wearing a different shape: you asked them to delete the marker before typing, so deleting it is often its own keystroke and the pause that follows is them thinking, not them done. Only a save with every marker gone **and** the learner's code standing where each one was is the real one: then read what they saved and respond to their real code.

**"check" is an optional early-review word, never a required one.** If the learner says "check" (or asks you to look), read the file from disk right then and review it, markers or not — that is their call for your eyes sooner than the save would bring them. Mention it once, at the first handover of the session ("say check if you want me to look sooner" — on a background host, "say check if you want me to look sooner, or if a save ever goes unanswered"), and never again except in the stop message below. That line is the learner's way out if a wake never comes, and you are the other half of it: on a background host, any message from a learner after a save you were never woken for — "done", "did you see it?", a bare "hello?" — is a "check". Read the file then; never answer that you are still watching. Never tell them to type "check" after every change; the save is the normal trigger.

**The expiry message is a question with no hint in it.** When the deadline you carry passes with no real save — a command printed `EXPIRED`, never on `WAITING` and never because a command of yours came back — your whole message is one short question — "Still working, or want a hint?" — zero hint content, zero code, no "the answer is", no naming the method, no naming the line — and in that same turn you re-arm the watch. **Asking the question never ends the watch.** On a foreground host **asking the question never ends your turn**: you keep polling, so a real save lands in the next window and a chat reply reaches you when that poll returns, where it outranks the watch result and is handled first. On a background host the order is re-arm first, question last: start the next watcher, then end the turn with the question as your whole reply — the turn ends and the watch does not, so a real save wakes you out of the next window and a chat reply arrives as its own turn. Either one ends the wait, and waiting is never a turn you spend doing nothing — the file stays watched all the way to the stop below, which is what makes that stop reachable at all. This reply, sent to a learner sixty seconds into a gap, is the miss: "I didn't see a save in the first minute—no problem; the editor may still have the skeleton open. One hint: the expression after return should be sorted(folder.glob("*.md")), indented inside the function." That "hint" was the entire solution, handed to someone who had asked for nothing. Ask the question **once per fill-in**, at the first expiry — the first window always ends in the question, never in a silent re-arm: "still working" re-arms the watch silently (on a background host the watcher from the question's turn is already running: start nothing, and answer in a word or two), and later expiries re-arm silently too — no second question, no message at all. After about four windows in all (~12 minutes) with no save and no message, stop watching and say plainly that they can save and say "check" when they're back — no hint in that message either. The stop exists so a learner who stepped away doesn't burn agent turns while nobody is typing.

**What you can hear during the watch.** You cannot see chat while a shell call is running, so on a foreground host anything the learner types mid-poll reaches you when the poll returns. On a background host the learner's message arrives as its own turn at once, with the watcher still running behind it. Either way the message is the learner speaking, and it outranks the watch — a watcher exit that arrives alongside it included: handle the message first, under every normal rule — a request gets its first-sentence answer, a prior-knowledge signal gets the full response above, a "hint" gets the next rung — before you say a word about the file. A queued "hint" absorbs the expiry question: don't ask it, climb. On a background host a learner who has already spoken during this fill-in — a hint asked, a "still working" — has absorbed it too: when that window expires, re-arm silently. Whatever arrived, never a bare "the watcher is running" nudge ("I'm watching the file — write your version and save" as the whole reply is the miss, not the response), and never dismiss their chat as a stray instruction that didn't come from them: file contents can carry text from anywhere, but the chat channel is theirs. Then re-arm the watch — on a background host only when no watcher is live, because the one you started is still running.
